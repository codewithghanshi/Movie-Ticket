TCS-504 SYSTEM DESIGN — ASSIGNMENT 1
MOVIE TICKET BOOKING SYSTEM
Language: C++

A. REQUIREMENT ANALYSIS

Functional Requirements

FR1 — Movie Listing: The system shall display all movies currently playing, including title, language and duration, when the customer selects the Movies option.

FR2 — Show Listing: After a customer selects a movie, the system shall display all shows for that movie with screen number and start time.

FR3 — Seat Display: After a customer selects a show, the system shall display every seat with its seat number, seat type and AVAILABLE/BOOKED status.

FR4 — Booking: A customer selects one or more seat numbers for a show. If any selected seat is already BOOKED, the whole booking is rejected and no seat changes state. A booking is confirmed only after payment succeeds.

FR5 — Pricing: The system shall calculate the booking amount from seat types using SILVER = Rs.150, GOLD = Rs.250 and PLATINUM = Rs.400.

FR6 — Payment: Exactly one payment method (UPI, Card or Cash) shall be used per booking. If payment fails, seats are released and the booking status becomes FAILED.

FR7 — Ticket Printing: After successful payment, the system shall print a ticket containing booking ID, movie, screen, start time, seat numbers, total amount and booking status.

FR8 — Cancellation: A customer shall be able to cancel a confirmed booking using its booking ID, after which all seats belonging to that booking shall become AVAILABLE again.

Non-Functional Requirements

NFR1 — Modularity: Each class shall be implemented in its own .cpp file so that responsibilities remain separated.

NFR2 — Extensibility: Adding another payment type should require a new Payment child class rather than changes to the existing payment implementations.

NFR3 — Input Validation: Invalid menu choices, show choices, seat numbers, duplicate seats and invalid payment choices shall be rejected with a clear message without crashing.

NFR4 — Maintainability: Functions should have one clear responsibility, use meaningful names, avoid magic numbers and keep repeated logic to a minimum.

C. CLASS RESPONSIBILITIES, DATA, METHODS AND MUST-NOT-DO

Movie
Knows: title, language, duration.
Does: provide movie information.
Must NOT: manage seats, bookings or payments.

Seat
Knows: seat number and seat type.
Does: provide physical seat information.
Must NOT: know booking status for a particular show.

Screen
Knows: screen number and its physical seats.
Does: create/own seats and find a seat.
Must NOT: manage bookings or payments.

Cinema
Knows: cinema name and screens.
Does: create/own screens and find a screen.
Must NOT: calculate booking prices.

Show
Knows: show ID, movie, screen, start time and ShowSeats.
Does: represent a screening and display its seats.
Must NOT: process payment or print tickets.

ShowSeat
Knows: one Seat and its status for one show.
Does: validate/book/cancel that seat.
Must NOT: calculate the whole booking amount.

Customer
Knows: name and phone.
Does: provide customer information.
Must NOT: directly change seat status.

Booking
Knows: booking ID, customer, show, selected ShowSeats, total amount and status.
Does: maintain booking state.
Must NOT: calculate prices or print tickets.

Payment (abstract)
Knows: payment contract.
Does: define pay(amount).
Must NOT: know booking seats or print tickets.

UpiPayment/CardPayment/CashPayment
Knows: its payment method.
Does: perform its payment behavior.
Must NOT: modify ShowSeat status directly.

PriceCalculator
Knows: seat-type prices.
Does: calculate total amount.
Must NOT: process payment or print tickets.

TicketPrinter
Knows: ticket formatting rules.
Does: print a ticket.
Must NOT: change booking state.

BookingService
Knows: movies, shows, bookings and service collaborators.
Does: orchestrate menu and end-to-end booking/cancellation flow.
Must NOT: contain payment-method-specific implementation or ticket-formatting logic.


D. RELATIONSHIP TABLE

| Pair | Choice | Justification using lifetime test |
| Cinema — Screen | Composition | Cinema creates and owns its Screen objects. If the Cinema is destroyed, its owned Screens no longer exist in this model. |
| Screen — Seat | Composition | Screen creates and owns its physical Seat objects. If the Screen is destroyed, those physical seats are destroyed with it. |
| Show — Movie | Aggregation | A Show refers to an existing Movie. The Movie can exist independently and can be used by multiple Shows. |
| Show — Screen | Association | A Show uses a Screen for a particular screening, but the Screen is an independently existing auditorium object. |
| Show — ShowSeat | Composition | Show creates the ShowSeat objects for that particular screening. If the Show is destroyed, its ShowSeat objects no longer exist. |
| Booking — Customer | Association | A Booking uses a Customer object; neither is the owner of the other's lifetime. |
| Booking — ShowSeat | Aggregation | Booking stores references to ShowSeat objects that are owned by the Show. Destroying the Booking does not destroy those ShowSeats. |
| Booking — Payment | Association | Payment performs a transaction for a Booking, but Payment is an independent service object and does not own the Booking. |
| Payment — UpiPayment/CardPayment/CashPayment | Inheritance | The concrete payment classes are specialized implementations of the abstract Payment contract. |
| BookingService — Booking | Aggregation | BookingService keeps confirmed bookings in a collection, but a Booking is an independent entity with its own identity. |

G. SOLID MAPPING

1. Single Responsibility Principle (S)
Booking does not print tickets. TicketPrinter owns ticket formatting/printing. PriceCalculator owns pricing. This separates reasons to change.

2. Open/Closed Principle (O)
Payment is abstract. A new payment method such as NetBanking can be added as a new Payment child without changing existing payment classes.

3. Liskov Substitution Principle (L)
UpiPayment, CardPayment and CashPayment implement the same Payment::pay() contract and can be used through a Payment pointer/reference.

4. Dependency Inversion Principle (D)
BookingService works with the Payment abstraction rather than depending on a specific payment implementation in its payment-processing logic. The selected concrete payment is supplied through the Payment base type.

One thing deliberately NOT done:
The design does not create a separate Refund interface or force every Payment class to support refund(), because the assignment does not require refunds. Adding unused behavior would make the Payment abstraction unnecessarily large.


CLEAN-CODE CHECKLIST

- Meaningful names such as bookedSeatCount, totalAmount and bookingId.
- No list1/list2-style names.
- Functions have focused responsibilities.
- Constants are used for seat prices.
- Ticket printing is not mixed with price calculation.
- showSeats/displaySeats only displays state and does not book seats.
- Payment behavior is not duplicated across all payment methods.
- Input validation is included for invalid choices and seat numbers.
